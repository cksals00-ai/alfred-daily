# 주간 키워드 레이더 — 설정 가이드

기준 문서 확인: 이 문서(2026-08-07 신설) · 화면은 뉴스 인사이트 탭 하단 「주간 키워드 레이더」

## 이게 뭔가

24개 키워드가 지난 한 주에 기사에 몇 번 나왔는지 세고, 그 앞 7일과 비교해
늘었는지 줄었는지를 보여주는 축이다. 일요일에 한 번만 돈다.

세는 대상은 **보도량**이지 관심량이 아니다. 「호캉스 84건 ▼37%」는 사람들이
호캉스에 덜 관심을 가졌다는 뜻이 아니라 **기자들이 덜 썼다**는 뜻이다. 이 구분을
흐리면 레이더는 곧 아무 말도 안 하는 그래프가 된다. 실제 검색량은 검색어 트렌드
API가 열려야 겹칠 수 있고, 그건 아직 구독 대기 상태다(맨 아래 참고).

## 무엇을 어떻게 세는가

네이버 API HUB 검색 API(뉴스)를 쓴다. 엔드포인트는
`GET https://naverapihub.apigw.ntruss.com/search/v1/news`,
파라미터는 `query` · `display=100` · `start=1/101/201…(최대 901)` · `sort=date`.
인증 헤더 두 개(`X-NCP-APIGW-API-KEY-ID`, `X-NCP-APIGW-API-KEY`)는 예약작업
프롬프트 안에만 있다. **이 문서에도, dashboard.html 에도, 어떤 로그에도 적지 않는다** —
longblack-daily.higgsfield.app 은 로그인 없이 열리는 공개 정적 사이트다.

집계에서 제일 중요한 규칙은 이것이다. **네이버 검색 응답을 그대로 세면 안 된다.**
검색 엔진이 단어를 쪼개서 매칭하기 때문에 「롯데호텔」로 부르면 롯데 울산 공장
기사가 섞여 들어온다. 그래서 응답을 받은 뒤

1. 제목·본문에서 `<b>` 태그를 제거하고,
2. 키워드가 **문자 그대로** 들어 있는 기사만 남기고,
3. 띄어쓰기 변형도 후보에 넣는다(「한화리조트」와 「한화 리조트」를 같은 것으로 본다).

키워드마다 최신순으로 페이지를 넘기며 **14일 전 날짜에 닿을 때까지** 스캔한다
(최대 10페이지 = 1,000건). 거기서 이번 주 7일 건수를 `cur`, 그 앞 7일 건수를
`prev`, 이번 주 상위 기사 3건을 `top` 으로 뽑는다.

한 번 도는 데 약 84콜이다. 무료 한도는 월 775,000 · 일 25,000이라 열 배로 늘려도
유료 구간에 닿지 않는다.

8/2(추가 이전)이라는 뜻이고, 다음 일요일 실행부터 6그룹으로 바뀐다.

## 데이터 형태

dashboard.html 안의 `const TREND_PLAN = {…}` 한 덩어리를 통째로 교체하는 방식이다.

```js
{
  status: "live-news",        // 실측 뉴스 기반. 추정치를 쓰는 모드는 없다
  updated: "2026-08-02",      // 실행일(일요일)
  weekFrom: "2026-07-27",     // 이번 주 시작
  weekTo:   "2026-08-02",     // 이번 주 끝
  calls: 70,                  // 이번 갱신에 쓴 API 콜 수
  groups: [
    { name: "리조트·호캉스",
      kw: [ { n: "호캉스", cur: 84, prev: 134,
              top: [ { t: "기사 제목", u: "원문 링크" } ] } ] }
  ]
}
```

`renderTrend()` 는 손대지 않는다. 데이터만 갈아끼우면 화면이 따라온다.

## 화면이 계산하는 것

증감률은 `(cur − prev) / prev × 100` 이다. `prev` 가 0이면 비율을 내지 않고
「신규」로 표시한다 — 0으로 나눈 값을 ∞나 100%로 적으면 거짓말이 된다.

맨 위 **급등·급락 칩**에는 아무 키워드나 올라오지 않는다. `prev ≥ 10` 이고
`cur + prev ≥ 40` 인 키워드만 후보가 되고, 그중 증감률 상위 2개와 하위 2개만
칩이 된다. 표본이 작으면 3건 → 6건도 +100%가 되는데, 그 숫자를 「급등」이라고
부르면 레이더가 매주 헛소리를 하게 된다. 이 문턱은 그걸 막는 장치다.

막대 길이는 **그룹 안에서만** 정규화된다(그룹 최댓값 = 100%). 그룹이 다른 두
막대의 길이를 서로 비교하면 안 된다. 그래서 막대 옆에 건수를 항상 같이 적는다.

키워드 줄을 펼치면 그 주 상위 기사 3건 링크가 나온다. 기사가 없으면 「이번 주
기사 없음」으로 남긴다 — **0건은 측정된 0이고, 조회 실패와 다르다.**

## 언제·누가 도는가

| 항목 | 값 |
|---|---|
| 담당 예약작업 | GS·인사이트 09:00 KST `trig_01QM65z2VTBqfM4AB5Zgd9dD` (cron `0 0 * * *`) |
| 실행 조건 | **일요일에만** — 오늘이 일요일이 아니면 이 단계를 통째로 건너뛴다 |
| 해당 단계 | 프롬프트 §3 「뉴스 인사이트 — 주간 키워드 레이더」 |
| 신선도 임계 | 정상 7일 / 주의 9일 (`tools/crawler/freshness.py` 의 TREND_PLAN 행) |

## 키워드를 바꾸려면

키워드 목록은 dashboard.html 이 아니라 **예약작업 프롬프트 §3 안에** 있다.
화면의 `TREND_PLAN` 은 매주 통째로 교체되는 결과물이라, 거기만 고치면 다음
일요일에 원래대로 돌아온다.

절차는 이렇다.

1. `list_triggers` 로 `trig_01QM65z2VTBqfM4AB5Zgd9dD` 를 찾는다
   (프롬프트는 `job_config.ccr.events[0].data.message.content` 에 있다).
2. §3 의 「24개 키워드 6그룹」 줄에서 그룹·키워드를 고친다.
3. `update_trigger` 로 `prompt` 전체를 교체한다. 트리거 객체에 최상위 `prompt`
   키는 없다 — 반드시 프롬프트 문자열 전체를 넘긴다.
4. 콜 수를 다시 센다. **키워드 1개당 최대 10콜**이다(24개 = 84콜). 키워드를
   40개로 늘려도 140콜이라 한도에는 여유가 있다.
5. 다음 일요일 실행 결과에서 그룹 수와 키워드 수가 맞는지 확인한다.

키워드를 고를 때 지킬 것 두 가지. 첫째, **문자 그대로 매칭이 되는 말**이어야
한다. 「호텔 마케팅」처럼 흔한 두 단어의 조합은 표제어로는 잘 안 쓰여서 0건이
계속 나온다. 둘째, **주당 10건 이상 나오는 말**이어야 급등·급락 문턱을 넘는다.
너무 좁은 말은 매주 「이번 주 기사 없음」만 남기고 화면 자리만 차지한다.

## 아직 안 되는 것

검색어 트렌드(`POST https://naveropenapi.apigw.ntruss.com/datalab/v1/search`)와
쇼핑 인사이트는 Application 에서 아직 구독되지 않아 401
`"A subscription to the API is required"` 가 난다. 일요일마다 한 번씩 찔러보고,
200 이 오면 그때 실제 검색량을 TREND_PLAN 에 얹는다. 그러면 「기사가 몇 건
나왔나」 위에 「사람들이 실제로 몇 번 검색했나」가 겹쳐진다 — 보도량과 관심량이
갈라지는 지점이 이 레이더에서 제일 값진 신호가 될 자리다.

## 읽을 때 조심할 것

14일 창을 최대 1,000건까지만 스캔한다. 어떤 키워드가 2주에 1,000건을 넘기면
그 주는 절단되어 실제보다 적게 세어진다. 지금 24개 중에는 그런 키워드가 없지만,
대형 이슈가 붙은 브랜드를 새로 넣을 때는 이 상한을 먼저 확인한다.

그리고 조회에 실패한 키워드는 **0으로 채우지 않는다.** 0은 「측정된 0」을
뜻하기 때문이다. 실패는 실패로 남기고 사유를 적는다.
