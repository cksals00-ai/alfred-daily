# 아침뉴스 재현본 파이프라인

기준 문서 확인: 이 문서(2026-08-03 신설)

## 이게 뭔가

alfred 가 매일 받는 「간추린 아침뉴스」를 자동으로 재현해 보고, 그가 붙여넣은
**원문과 대조해 점수를 매기고, 그 점수로 다음 날 수집 규칙을 고치는** 루프다.

```
digest.py  수집·편집 → app/public/digest.json   (재현본, 날짜별)
              ↕ 대조
alfred 붙여넣기 → app/public/news.json          (원문, src:"원문" 로 표시)
              ↓
score.py   채점 → rubric.json                   (재현율·정확도·누락 카테고리 누적)
              ↓
           digest.py 의 SLOTS / SEEDS / GUARD 를 고친다
```

## 왜 레포 안에 있나

예약작업은 매번 **새 컨테이너**에서 레포를 클론해 돌린다. 이전에는 이 스크립트가
`/home/claude/work/crawler/` 에만 있어서 예약 실행 때 없는 파일이었고, 그래서
2026-08-01 부터 재현본이 웹검색 수기 수집으로 대체되며 꼭지 수가 16 → 9 → 5 로
떨어졌다. 레포 안에 두면 클론만으로 항상 존재한다.

자격증명은 레포에 넣지 않는다(공개 저장소다). `_paths.cred()` 가 환경변수 →
작업폴더 `.naver.json` 순으로 찾고, 둘 다 없으면 **추정하지 않고 예외를 낸다.**

## 채점 규칙

- `src == "원문"` 인 날만 채점한다. 재현본을 news.json 에 그대로 써 넣은 날을
  채점하면 자기 자신과 비교해 재현율이 100% 로 나온다 — 측정이 아니라 착시다.
- **재현율** = 원문 꼭지 중 재현본이 잡은 비율 (놓친 사건을 본다)
- **정확도** = 재현본 꼭지 중 원문에도 있던 비율 (헛다리를 본다)
- 매칭은 어간 기준 핵심어 겹침이다. 한국어 조사 때문에 `여객선` 과 `여객선에`
  가 다른 토큰이 되므로 뒤 한두 글자를 떼어 함께 비교한다.
- 매칭은 완벽하지 않다. **같은 주제·다른 각도**(예: 원문 "구마모토 반도체 공장
  재가동" ↔ 재현본 "구마모토 강진 수색 종료")는 누락으로 잡힌다. 점수는 절대값
  보다 **추세**로 읽는다.

## 지금까지 확인된 것 (2026-08-03 기준, 정본 1일)

재현율 12% · 정확도 40%. 누락 카테고리는 정치·국회 4, 사건·사고 4, 국제·안보 3,
경제·시장 2, 부동산 1, 날씨·기후 1.

원문과 재현본의 성격 차이가 구조적으로 드러난 부분:

1. **원문은 "오늘 무엇이 예정돼 있나"를 쓴다.** 재현본은 어제 보도량이 많았던
   기사를 쓴다. 원문 1번 꼭지가 "귀국 직후 점검 회의를 엽니다"인데 재현본은
   "귀국했다"를 잡는 식이다. → `sort=date` 만으로는 예고성 기사를 못 잡는다.
2. **원문은 생활·사건·사고를 많이 쓴다.** 신림동 상가 화재, 군산 방사선사,
   차은우 조세심판 — 보도량은 적지만 사람들이 읽는 것들이다. 재현본의 슬롯
   배정(정치 5)이 실제 분포와 다르다.
3. **원문은 숫자를 꼭 넣는다.** "온열질환자 96명 늘어 누적 1,889명, 사망 14명".
   재현본은 제목·요약을 그대로 옮겨 숫자가 빠진다.
4. **원문은 두 문장으로 재작성한다.** 재현본은 네이버 요약문을 그대로 쓴다.

## 개선 백로그 (근거가 쌓이는 대로 반영)

- [ ] 슬롯 배정을 정본 누적 분포로 재산출 (현재 SLOTS 는 348일치 역산값이지만
      카테고리 분류가 거칠다)
- [ ] 사건·사고/사회·생활 씨앗어 확장 — 화재·사망 중심에서 생활 사건으로
- [ ] 예고성 기사 가중 — "오늘", "예정", "열린다" 가 제목에 있는 기사 가산
- [ ] 숫자 보존 — desc 에서 수치 표현을 우선 남기는 재작성 규칙
- [ ] 두 문장 재작성 (현재는 제목+요약 그대로 붙임)
- [ ] **단일 대형 이슈 날의 슬롯 탄력 배분** (2026-08-04 근거) — 원문 13꼭지 중 6꼭지가
      폭염이었다(중대경보·상권·온열질환자·정전·경남 40도·열대야 13일째). 재현본은 날씨
      슬롯이 고정 1~2개라 6개 중 2개만 잡았다. 특정 카테고리 기사량이 임계를 넘는 날은
      그 슬롯을 늘리고 다른 슬롯을 줄이는 규칙이 필요하다. 고정 배분은 평시엔 맞지만
      이런 날엔 구조적으로 틀린다.
- [ ] 사건·사고·정치 누락 집중 (정본 2일 누적: 사건·사고 6 · 정치·국회 5 · 국제·안보 4) —
      다만 8/3 은 구 파이프라인 5꼭지 재현본이라 표본 오염. 정본 3일+ 쌓인 뒤 재평가.

## 신선도 점검 (freshness.py)

score.py 가 "재현본이 얼마나 정확한가"를 본다면, freshness.py 는 그 앞의 질문 —
**"애초에 갱신이 돌긴 했는가"** — 를 본다. 둘은 다른 실패다. digest.py 가 컨테이너에서
사라진 채 몇 주를 돌았을 때 화면은 멀쩡했다. 어제 데이터가 남아 있으면 오늘 것처럼
읽히기 때문이다. 그 침묵을 깨는 게 이 스크립트다.

12개 소스의 **최신 날짜만** 읽는다. 담당 예약작업을 함께 찍어서, 멈춘 축이 있으면
어느 작업을 봐야 하는지가 바로 나온다.

| 축 | 담당 예약작업 | 임계(정상/주의) |
|---|---|---|
| news.json · digest.json | Alfred Daily 07:00 `trig_01AJNUPpjXMmddzqkpoQJ2iX` | 1일 / 2일 |
| insta.json | 같은 작업 §0 (교신함 수급) | 1일 / 2일 |
| GS_DAILY · INSIGHT_DAILY | GS·인사이트 09:00 `trig_01QM65z2VTBqfM4AB5Zgd9dD` | 1영업일 / 2영업일 |
| GS_PERF.asOf | 같은 작업 §1-b | 2영업일 / 3영업일 |
| GS_PERF.fcstAsOf | 같은 작업 (주간 스냅샷) | 7일 / 10일 |
| TREND_PLAN | 같은 작업 §3 (일요일만) | 7일 / 9일 |
| WEEKLY_BRIEF · NEWS_WEEKLY | 주간 브리핑 일 07:00 `trig_01NqusWzxt6ikGFZkKwRJ15C` | 7일 / 9일 |
| NOTES · TODAY_AGENDA | 없음 — 손으로 채운다 | 수동(참고만) |

설계상 지켜야 할 것 세 가지.

1. **GS 계열은 달력일이 아니라 영업일로 센다.** 출처 페이지가 주말·공휴일에 갱신되지
   않기 때문이다. 토요일마다 "하루 밀렸다"고 울리는 경보는 곧 아무도 안 본다.
2. **GS_PERF.asOf 는 임계를 한 칸 밀어 놓았다.** 출처가 전일 실적을 싣는 구조라
   1영업일 지연이 정상이다. 구조적 지연을 고장으로 부르지 않는다.
3. **수동 축은 실패로 세지 않는다.** 롱블랙 노트는 alfred 가 링크를 보낼 때만 늘어난다.
   공백은 고장이 아니라 그냥 공백이다. 경과일은 보여주되 판정은 「수동」으로 남긴다.

파일·상수를 못 읽으면 「조회실패 + 사유」로 남기고 넘어간다. 0으로도, 추정치로도
채우지 않는다.

## 사용법

```bash
python3 tools/crawler/digest.py            # 오늘치 재현본 생성 + digest.json 갱신
python3 tools/crawler/score.py 2026-08-03  # 하루 채점
python3 tools/crawler/score.py --all       # 정본 전체 누적 + rubric.json 기록
python3 tools/crawler/freshness.py         # 12개 소스 신선도 표 + freshness.json 기록
python3 tools/crawler/freshness.py --line  # 보고용 한 줄만
```
